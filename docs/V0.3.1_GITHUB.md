# V0.3.1 — Versionamento GitHub

## Estratégia

O Delivery Hub utiliza uma estratégia simples:

```text
main
  |
  +-- commits estáveis
  |
  +-- tag v0.3.1
  +-- tag v0.3.2
  +-- tag v0.4.0
```

Branches `feature/*` são usadas apenas quando uma mudança maior precisa ficar
isolada antes de chegar à `main`.

## Primeiro uso

```text
BAT/GITHUB/01_CONFIGURAR_REPOSITORIO.bat
```

Por padrão, o repositório é criado como privado.

O BAT:

1. verifica Git;
2. instala/verifica GitHub CLI;
3. abre autenticação oficial do GitHub;
4. inicializa `.git`;
5. configura identidade Git somente neste repositório;
6. confere arquivos ignorados;
7. executa validação do projeto;
8. cria o repositório remoto;
9. envia `main`;
10. cria a tag da versão atual.

## Trabalho intermediário

```text
BAT/GITHUB/02_SALVAR_TRABALHO.bat
```

Isso cria um commit e envia a branch atual sem criar uma tag.

## Versão aprovada

Primeiro atualize a versão no `package.json`.

Depois:

```text
BAT/GITHUB/03_PUBLICAR_VERSAO.bat
```

Esse BAT:

- valida o projeto;
- cria commit de release se necessário;
- envia `main`;
- cria tag anotada `vX.Y.Z`;
- envia a tag;
- cria uma GitHub Release.

## Segurança

Arquivos como estes não podem ser enviados:

```text
firebase/projeto.local.env
firebase/web-sdk-config.raw.json
public/firebase-config.json
service-account*.json
firebase-admin*.json
dados-operacionais/
evidencias/
fotos-entrega/
```

O BAT de configuração verifica os três principais arquivos Firebase antes do
primeiro push.

## GitHub Actions

`.github/workflows/validar.yml` executa:

```text
npm ci
npm run check
```

em todo push para `main` e em Pull Requests direcionados à `main`.
