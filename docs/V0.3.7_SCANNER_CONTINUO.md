# V0.3.7 — Scanner contínuo ao vivo

## Objetivo

Substituir o fluxo principal de "tirar foto e depois tentar ler" por scanner de
câmera contínua. O entregador aponta o aparelho para o barcode/QR e recebe
confirmação antes de seguir.

## Fluxo

```text
abrir scanner
→ solicitar câmera
→ analisar quadros continuamente
→ detectar candidato
→ confirmar o mesmo código em 2 leituras
→ vibrar
→ fechar scanner
→ mostrar resultado
```

A fotografia permanece disponível apenas como fallback. Digitação/colar tracking
continua como último fallback.

## Segurança de leitura

- não escolhe cegamente o primeiro código retornado pelo detector;
- normaliza todos os candidatos encontrados;
- aplica as regras das transportadoras;
- prefere tracking reconhecido quando há também QR/conteúdo desconhecido;
- exige duas leituras próximas antes da confirmação;
- se mais de um tracking conhecido for confirmado, pede escolha manual;
- o modo homologação continua sem enviar baixa às transportadoras.

## Android

O build injeta `android.permission.CAMERA` no `AndroidManifest.xml` gerado pelo
Capacitor. A câmera é acessada com `navigator.mediaDevices.getUserMedia`, e o
Capacitor trata a solicitação de permissão no WebView Android.

## Regras observadas nesta homologação

- Anjun: agora aceita `AJ` + 14 dígitos e `AJ` + 15 dígitos, cada formato com
  regra identificável separadamente.
- iMile: teste real adicionado para `6082326246225`.

## Atualizações do APK

O Android recebe `versionName` e `versionCode` a partir da versão do `package.json`.
O workflow também preserva a chave debug de homologação pelo cache do GitHub Actions.
A V0.3.7 é a primeira versão desse novo modelo; por isso, ao sair da V0.3.6 pode ser
necessário desinstalar uma vez o APK antigo caso a assinatura anterior seja diferente.
A partir da chave preservada, homologações seguintes tendem a instalar como atualização.
A assinatura de produção continuará exigindo keystore própria e protegida.

## Pipeline GitHub

O BAT `07_GERAR_APK_HOMOLOGACAO.bat` também foi endurecido contra oscilações de
internet durante `gh run watch`. Uma queda de conexão local não é mais tratada
imediatamente como falha do build; o BAT tenta consultar o resultado do run
novamente antes de decidir.
